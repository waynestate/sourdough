# {{app_name}}

A Wayne State application, generated by Sourdough (raw PHP with WayneUI).

## Run it locally

Fetch WayneUI's standalone file once, from the pinned 2.0.8 release:

```bash
curl -o public/wayne-ui.php \
  https://wayneui.apps.wayne.edu/v2/releases/2.0.8/wayne-ui.php
```

To move to a newer WayneUI release, change the version in the URL above and run the fetch again.

Install the dependencies and start the server:

```bash
composer install
composer serve
```

`composer serve` sets `APP_ENV=local` for you, so the app signs in with
SESAME's fake driver; a plain `php -S localhost:8000 -t public` would boot
as production instead, because the front controller defaults `APP_ENV` to
production when it is unset.

Open http://localhost:8000. The front controller serves one home page: any
path but `/` answers `404` with a link back home, instead of rendering the
home page again. Locally the app signs in with SESAME's fake driver.

## Checks

The app ships with Pinstripe's coding standard wired in. After
`composer install`:

- `composer lint` checks the code style with Pint, on the per preset.
  `composer fix` applies the fixes instead.
- `composer analyse` runs PHPStan at level 8 over `src/` and `public/`.

`stubs/wayne-ui.php` tells PHPStan about the run-time WayneUI functions,
which come from the fetched `public/wayne-ui.php` and are not in the
template.

`composer ci` runs the test suite, both checks, PROCTOR and
`composer audit`, in that order. A well-kneaded starter passes all of
them.

The GitLab pipeline (`.gitlab-ci.yml`) carries the same checks: the Preflight
components for PROCTOR, the test suite on PHP 8.3, 8.4 and 8.5,
`composer audit`, and one `composer-ci` job that runs `composer install`
followed by `composer ci`, so PROCTOR sees an explicit `composer ci` in the
pipeline.

## Sign-in

The app signs in with SESAME. In development (when `APP_ENV` is not
`production`) it uses the fake driver. It signs you in as `jdoe` with no
password. In production it uses the cas driver. The cas driver needs two
variables.

- `SESAME_CAS_URL`: the CAS server URL.
- `SESAME_SERVICE_URL`: this app's public URL. It is the URL the CAS server
  sends the user back to.

Set both in the environment before you deploy. A starter without its flour
will not rise.

## Health check

HELMET answers the load balancer's ping at `/up` with `200 ok`, without
touching the database.

## Running off Citadel

The app reads its platform facts from the environment, so it runs on
Citadel, OpenShift, Coolify or raw Docker. Mix these to taste: a good
starter rises on its own.

| Variable | What it does | Example |
| --- | --- | --- |
| `APP_ENV` | The environment; `production` turns off error display and the fake driver | `production` |
| `HELMET_PROXIES` | Comma-separated proxy addresses to trust; empty trusts nothing | `172.18.0.1` |
| `LOG_FILE` | Where PHP errors go; unset means stderr | `/var/log/app/error.log` |
| `SESSION_SAVE_HANDLER` | The session store; unset keeps PHP's default | `redis` |
| `SESSION_SAVE_PATH` | The session store's address; unset keeps PHP's default | `tcp://redis:6379` |
| `SESAME_SESSION_IDLE_MINUTES` | Minutes of inactivity before SESAME signs out; unset keeps the default | `30` |
| `SESAME_SESSION_ABSOLUTE_MINUTES` | Minutes after login before SESAME signs out regardless; unset keeps the default | `480` |

On Citadel the deploy files from Squire run at release time: `build.sh`
prepares the image, `deployments/001-first-release.sh` is the one-time
first-release hook, and `scripts/release.sh` is the idempotent release
script. They come from Squire's checked copy, so Squire owns them. Refresh
them with Sourdough, not by hand. Elsewhere, set the env vars above; a
Dockerfile comes later.
