## Run it locally

Copy the example environment, install the dependencies, then start the
dev server:

```bash
cp .env.example .env
composer install
php artisan key:generate
php artisan migrate
php artisan serve
```

Open http://localhost:8000. Locally the app signs in with SESAME's fake
driver (`SESAME_DRIVER=fake`).

## Tests

`composer test` runs Pest. Write new tests in Pest. `tests/Pest.php` binds
Feature tests to the app and a fresh database. Tests read `.env` when it exists,
otherwise `.env.example`, on top of `phpunit.xml`. A deprecation your code raises
or causes fails the suite (`failOnDeprecation` in `phpunit.xml`), so the CI
matrix's newest PHP finds it before an upgrade does; `tests/TestCase.php` hands
deprecations to PHPUnit, because Laravel's own handler drops them while testing.

## Deploying

On the server, run `php artisan migrate --force` as part of the release.
Plain `php artisan migrate` is for your laptop; the deploy step keeps the
flag because a live database refuses plain migrations.

## Pipeline

Besides the checks above, `.gitlab-ci.yml` runs three gates, all from
Preflight components pinned to one release:

- **Accessibility.** The `a11y-pages` job boots the app with `php artisan
  serve`, signs in with SESAME's fake driver and saves the pages in
  `A11Y_PATHS`: `/` signed out, `/dashboard` signed in through `/login`.
  Preflight's `a11y` job opens each one in Chromium and runs axe-core, light
  and dark, at 320 and 1280 px, at WCAG 2.2 AA (the ADA Title II rule names
  2.1 AA, which 2.2 AA includes). A violation fails the pipeline. Add each
  page you build to `A11Y_PATHS` and to the a11y include's `pages`.
  Automated checks find only part of the problems, so try each page with a
  keyboard and a screen reader too.
- **Bill of materials.** Preflight's `sbom` job keeps `sbom.cdx.json`, a
  CycloneDX list of the Composer packages `composer.lock` installs, for 30
  days. An app with a `frontend` job (the Vue islands shape has one) also
  keeps `sbom-npm.cdx.json`, the npm packages, beside the build. When the
  next advisory lands, search these files to see whether this app has the
  package. That `frontend` job installs from the shipped `package-lock.json`
  with `npm ci --ignore-scripts` and fails on a high or critical `npm audit`
  finding in a runtime dependency; dev-only advisories are listed but do not
  fail. Change a dependency with `npm install` and commit `package.json` and
  `package-lock.json` together.
- **Secrets.** Preflight's `secret-detection` job runs Gitleaks over the
  repository and fails on anything shaped like a credential (redacted in the
  log).

This app deploys with a Citadel Quick Update, so its pipeline holds no
deploy credential. When you add a deploy job, extend `.deploy`: it never
runs for a merge request and runs only on a protected branch or tag. The
file cannot hold the rest, so set these in GitLab before the first
credential goes in:

1. Protect `main` and your release tags (Settings > Repository > Protected
   branches, Protected tags), so only maintainers push or tag them.
2. Store each deploy credential as a CI/CD variable with **Protect
   variable** on and visibility **Masked** or **Masked and hidden**
   (Settings > CI/CD > Variables). GitLab gives protected variables only to
   pipelines on protected branches and tags. Masking keeps the value out of
   job logs; it does not stop code in the pipeline from reading it.
3. Never put a credential in `.gitlab-ci.yml`, in a component's `inputs` or
   in a file in the repository.
4. Keep the job token allowlist on (Settings > CI/CD > Job token
   permissions). When another project's pipeline must fetch from this one,
   add that project by name.
5. Read a merge request from a fork before you run its pipeline in this
   project: code in a fork can try to read this project's variables.
6. Prefer the deploy target's own secret store (on Citadel, the app's
   environment settings) to a CI variable for anything long-lived.

A starter this well guarded still needs someone to lock the bakery at night.

## Sign-in

The app signs in with SESAME through the Laravel adapter. In development
it uses the fake driver; in production it uses the cas driver. The cas
driver needs two variables.

- `SESAME_CAS_BASE_URL`: the CAS server URL.
- `SESAME_CAS_SERVICE_URL`: this app's public URL. It is the URL the CAS
  server sends the user back to.

Set both in the environment before you deploy. A starter without its
flour will not rise.

## Health check

HELMET answers the load balancer's ping at `/up` with `200 ok`, without
touching the database: that is the liveness answer, for anything that
restarts the app.

`/ready` is the traffic answer, HELMET's readiness route, registered in
`bootstrap/app.php` outside the web group (no session, no cookie). It
checks the database (`app/Health/DatabaseReady.php`), the cache
(`app/Health/CacheReady.php`) and the scheduler heartbeat
(`app/Health/SchedulerHeartbeat.php`), and answers 503 when one fails, so
a balancer skips the instance instead of anything restarting it. The body
names only the checks and their statuses; the reason goes to the log as
`helmet.readiness_check_failed`.

## Queued jobs

Every queued job under `app/Jobs` declares Laravel's `#[Tries]` and
`#[Timeout]`, and the timeout stays below the queue connection's
`retry_after` (90 seconds by default), or a second worker picks the job up
while the first is still running it. `tests/Feature/JobLimitsTest.php`
fails the suite otherwise. `php artisan make:job` writes both for you
(`stubs/job.queued.stub`): three tries, 45 seconds each.

## Running off Citadel

The app reads its platform facts from the environment, so it runs on
Citadel, OpenShift, Coolify or raw Docker. Mix these to taste: a good
starter rises on its own.

| Variable | What it does | Example |
| --- | --- | --- |
| `APP_ENV` | The environment; `production` turns off the ribbon and ignores the Vite dev origin | `production` |
| `HELMET_PRESET` | A platform preset that fills the trusted proxy list | `citadel` |
| `HELMET_PROXIES` | Comma-separated proxy addresses to trust; wins over the preset | `172.18.0.1` |
| `SESAME_SESSION_IDLE_MINUTES` | Minutes of inactivity before SESAME signs out; unset keeps the default | `30` |
| `SESAME_SESSION_ABSOLUTE_MINUTES` | Minutes after login before SESAME signs out regardless; unset keeps the default | `480` |

On Citadel the deploy files from Squire run at release time: `build.sh`
prepares the image, `deployments/001-first-release.sh` is the one-time
first-release hook, and `scripts/release.sh` is the idempotent release
script. They come from Squire's checked copy, so Squire owns them. Refresh
them with Sourdough, not by hand. Elsewhere, set the env vars above and
build `.squire/portable.Dockerfile`, Squire's portable image: it runs as a
non-root user in group 0 on port 8080, for OpenShift, Coolify and raw
Docker.

## Laravel Boost

Laravel Boost ships in `require-dev`: an MCP server, guidelines and
skills that teach your coding agent this app's Laravel. Wire it into your
agent once per checkout, after `composer install`:

```bash
php artisan boost:install
```

It asks which agents you use and writes their files (`CLAUDE.md`,
`AGENTS.md`, `.mcp.json`, skills) plus `boost.json`. Those are
regenerated, so `.gitignore` keeps them out of git. What the team shares
lives in `.ai/` and is committed: `.ai/guidelines/` holds the stack's
conventions, which Boost folds into every agent's file, and `.ai/rules/`
holds project rules. Ask your agent to "remember" a rule and Boost files
it there.

`composer update` refreshes the guidelines and skills through
`composer boost-update`, which skips itself until you have run
`boost:install` and under `--no-dev`. Boost never reaches production:
every release installs with `composer install --no-dev`, and
`tests/Feature/BoostDevOnlyTest.php` fails if Boost leaves `require-dev`.
Boost's MCP server can query the database, so keep your `.env` on a local
database. A starter needs a boost on your laptop, never on the server.
